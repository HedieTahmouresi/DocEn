# Document Scanning & Enhancement

A CNN-based document scanner built from scratch for a university Computer Vision course. It
detects the four page corners in a phone photo, rectifies the perspective, and enhances the
rectified crop into a clean scan — the core of what CamScanner and Adobe Scan do.

```
Raw phone photo → corner detector → perspective rectification → enhancement network → clean scan
```

The two networks are **trained and evaluated independently** and only chained together in the
bonus part. Both are trained entirely on synthetic data — clean scans warped onto random
backgrounds and degraded — and evaluated on real smartphone photos with hand-annotated corners.


```bash
pip install -r requirements.txt
```

`data/` is not in the repository. It must contain:

```
data/clean_scans/      the provided clean document scans (ground-truth targets)
data/backgrounds/      background photographs for compositing
```

## Configuration

Configs are layered `base.yaml → env/<name>.yaml → exp/<name>.yaml`, later layers overriding
earlier ones. The fully resolved config is written to the run directory, so every result is
reproducible from its own directory.

Pick the environment with `--env`. **A missing or misspelled profile raises** — it used to be
skipped silently, which meant a `--env colab_t4` run could quietly execute on CPU.

| Profile | Device | AMP | Batch | For |
|---|---|---|---|---|
| `local_cpu` | CPU | off | 2 | verification scripts, figures, smoke tests |
| `mx330` | CUDA | off | 2 | laptop smoke tests (4.2 GB VRAM, Pascal — AMP is not worth it) |
| `colab_t4` | CUDA | on | 8 | the real training runs |

`batch_size` deliberately lives in the environment profile, not in the experiment config: it is a
property of the GPU, and every arm of an ablation must share it, or BatchNorm statistics differ
and the comparison is confounded.

## Running

```bash
# One-off: build the frozen evaluation sets
python -m src.data.freeze

# Sanity ladder — always before a long run
python -m pytest tests/ -q

# A short end-to-end smoke run
python train_ablation.py --env local_cpu --epochs 2 --samples-per-epoch 40

# The loss ablation — all four arms on one data stream
# (see notebooks/colab_train.ipynb for the Colab version)
python train_ablation.py --env colab_t4 \
    --mirror-dir /content/drive/MyDrive/DocEn_runs --mirror-every 5

# Resume an interrupted suite — continues every arm from its own last.pt
python train_ablation.py --env colab_t4 --resume

# One arm on its own, if you need it
python train.py --config configs/exp/exp-005_enh_mse.yaml --env colab_t4
python train.py --config configs/exp/exp-005_enh_mse.yaml --env colab_t4 \
    --resume runs/exp-005_enh_mse/checkpoints/last.pt

# Figures, restored samples, and the summary table vs the no-model baseline
python -m scripts.evaluate_ablation
python -m scripts.save_restored_samples
```

### Why `train_ablation.py` exists

The four arms differ only in the loss. Running `train.py` four times regenerates the same
80,000 synthetic samples four times over, and the generator — not the GPU — is what sets the
pace on a 2-vCPU Colab runtime. Training all four on one stream removes that redundancy, and
makes the comparison *paired*: every arm sees the same batches in the same order, from
identical initial weights. It refuses to start if the configs disagree on anything but the
loss, which is the phase-04 gate item "identical seed, architecture, schedule, batch size and
frozen sets" checked at launch rather than by eye.

A NaN in one arm fails that arm alone; the others carry on. Estimated 2.5–3.5 h for the suite
versus 5–6 h sequential — an estimate, not a measurement; check `epoch_seconds` after epoch 1.

## Conventions

| Stage | Layout | Range | Colour |
|---|---|---|---|
| disk / `cv2.imread` | HWC uint8 | 0–255 | BGR |
| degradation pipeline | HWC uint8 | 0–255 | BGR |
| model input | NCHW float32 | standardised | RGB |
| target / output / metrics | NCHW float32 | `[0, 1]`, `data_range=1.0` | RGB |

Corners are ordered **TL → TR → BR → BL**, clockwise from the top-left *of the page*, and are
normalised by dividing by width and height. Points are `(x, y)`; NumPy indexes `img[y, x]`.

Normalisation is asymmetric on purpose: the input is standardised with statistics computed from
the training split only, while the target, the output and every metric stay in `[0, 1]`. Anything
that displays or scores a model *input* must un-standardise it first — see
`src/data/normalization.py`.

## Constraints

- **PyTorch** for all models, datasets and training
- **No pre-trained weights** anywhere — which also rules out VGG/LPIPS perceptual losses
- **No imported architectures** — the U-Net is written from `nn.Conv2d`, `nn.MaxPool2d`,
  `nn.ConvTranspose2d`, `nn.Linear`
- **OpenCV + NumPy only** for the degradation pipeline — no albumentations, no imgaug, no
  `torchvision.transforms`
- **No dropout and `weight_decay = 0`** in the first version of every network; both are asserted
  at startup. Dropout arrives only as a measured comparison in Phase 07.
- **No flips** — mirrored text is not something a document scanner should learn to restore
- **Never train on the real photos**, and never run the degradation pipeline on them
- **Never touch the synthetic test split** until the final evaluation
